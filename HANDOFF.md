## Chart laws (user's rules, do not regress)
- Frame = single night **anchored to UTC** (round 6, supersedes the local-noon/local-midnight law): left edge **12:00 UTC**, exact centre **00:00 UTC**, right edge **12:00 UTC +1 day**, at every site and in every season (REQUIREMENTS §4.1). `geom.frameOf` derives it: `midSec = round((frameNoon + 12 h) / 86400) * 86400`, `noonW = midSec − 43200`, `noonEndW = midSec + 43200` — `frameNoon` (the site's local noon) only picks WHICH night, the clock scale is UTC. Accepted consequence, chosen knowingly by the reviewer: far from UTC the sky wraps inside the frame (Sydney +11 reads dark → dawn → daylight → dusk → dark, daylight mid-chart).
- **One clock scale, named ONCE, no suffixes** (round 5 put the clocks on UTC, round 6 widened the "UTC" suffix, round 7 deleted every suffix as clutter): the axis corners, centre clock, transition labels, rise/set chips (`rise 14:57` / `set 06:26`), now-chip, tooltip, header title and summary strip labels are all on the UTC scale and print no designation. The scale is named in exactly one place, the header label **`Local Time (All chart elements UTC)`** (`Planner.tsx`, `.hint` span keeps its own casing under the uppercase label). That box is the only local clock on the page; the ±1 h zone nudge is gone for good — `fmtClock(instant, tz, h12)` off the IANA zone already follows the summer/winter switch.
- **A night change carries the focus marker; it never snaps back to the clock** (round 7, item 6): `scrub.carryFocus(prev, next, scrubbed, live)` moves the focus by `Math.round((next.midSec − prev.midSec) / DAY_SEC)` days and nothing else, so the red line and the moon glyph on it hold their exact pixel while the sky changes — this is what makes the round-5 night flipbook usable. A live marker hands over as a scrub (`⏱ live` re-arms it); a same-night edit keeps live. Never "helpfully" re-centre or re-arm on a new payload, and never park the focus on a moonrise (that pre-step ping-ponged between nights and tripped React's update-depth guard in round 3).
- **ZONE is a dropdown of real IANA zones, built offline** (round 7, item 4): `lib/chart/timezones.ts` holds the ~100-entry anchor table, `zoneOptions(nightMs, savedZone)` builds entries ordered by the offset each zone uses **on the night displayed** (`Europe/Prague · UTC+1` in November, `· UTC+2` in June) and `nearestZone(lat, lon)` auto-picks one when a coordinate commits. No network, no geo service, §6 contract unchanged (the planner still receives a zone name), fixed 210 px control. Never replace it with a numeric offset list: that cannot follow DST and the planner would reject it.
- **Focus is a real epoch everywhere** (round 5 fix): slider value, marker, typed time, ±1 h steps and live clock all share the payload's `Date.parse(ISO)` number line (`epochAtWall` is the only wall→instant conversion, and it iterates to a fixed point so DST is exact). Never reintroduce wall-fields-as-UTC.
- **Scrubbing NEVER changes the chart or the night.** Slider min/max are real epoch seconds spanning exactly `12:00 UTC → 12:00 UTC +1 day` (Prague fixture `min=1795435200 max=1795521600`, exactly 86400 apart), unclamped-value pattern; ±1 h buttons clamp at the edges and never flip days. Day changes ONLY via the Planner header stepper (◀ / "tonight" / ▶, parent state — the chart's own `shiftNight()` and the `planner:date` window events are gone since round 7).
- **Moon glyph is NOT drawn while below horizon** (round 5, replaces the park-at-crossing rule). `glyphSecOf` returns null when alt ≤ 0; readout says "below horizon". Focus still moves freely, no snapping.
- Rise/set chips: bottom edge on the **10° altitude line**; outside-of-curve preference kept, but when there is no room they **clamp to the plot edge on their own side** instead of flipping across the arc; flip only when the arc intrudes > 12 px (arc sampled at t=0.25/0.5/0.75, not just endpoints). ## FIXED (round 5, 24 Nov) — focus axis vs frame axis
The defect below is **fixed and gated**; keep the shape of the fix, do not regress it.
`focusSec()` and `liveSec()` used to carry a focus as `Date.UTC(wall fields)` while the frame and every payload sample are real epochs (`Date.parse(ISO)`), so the focus sat one zone-offset right of the axis it was drawn on: scrubbing to 13:00 in Prague drew at x=131 instead of 93.5 (+37.5 px) and the readout said 14:00; Sydney was off by +11 h (412 px). Same root cause behind the typed-time box landing on the wrong hour in far-east zones — and behind round-5 items B1 (could not scrub earlier than 14:00, marker vanished past noon), B2 (−1 h looked like it stepped forward) and B3 (typed 22:00 drew at 01:00).
The fix: one number line. `clock.ts` gained `epochAtWall(y,mo,d,h,mi,s,tz)` — a ≤3-iteration fixed point (`e -= drift`) returning **seconds** — and `focusSec`/`focusAt`/`liveSec`/`typedFocus`/`scrub*` all read and write real epoch seconds; `withZoneOffset` / `utcDayOfInstant` / `midnightLabel` are gone. `units.ts` now pins it: axis edges are real instants, `xOf(epochAtWall(…13:00…)) - xOf(f,noonW) === 37.5` in BOTH Prague and Sydney, a ±1 h step moves the marker exactly 37.5 px in the right direction, and a typed 03:30 sits exactly 3.5 h right of local midnight. `withZoneOffset`-style pseudo-seconds must never come back. (Round 6 re-pinned the wording of two of these assertions — the left edge is 12:00 UTC, not local noon — so today the real-epoch checks read "13:00 **UTC** sits 37.5 px right of the left edge" and `epochAtWall(local 13:00) === f.noonW + 3600` at Prague; the shape of the fix is unchanged.)
Why it was invisible to the gates before: neither render gate draws the marker or the slider in SSR, so only the pure-function gate could see it.

## Portability — verdict (full detail: `docs/PORTABILITY.md`)
Plain-language summary, so you do not have to decode ARCHITECTURE §5:
- **Nothing is entangled.** Astronomy = one Python module (`planner/night.py`); the UI
  is a plain browser client that asks one JSON endpoint (`/api/night`). Every target
  shape reuses that seam. No Next-server features are used at all (`next.config.ts` is
  empty, no API routes/middleware), so the UI is already host-agnostic.
- **Public web app = easy, and it is step 1.** One blocker: `web/app/lib/api.ts:7-8`
  bakes the API origin in at **build** time (`NEXT_PUBLIC_API_BASE`). Make it
  same-origin (`/api/night` proxied by the host) or runtime-configurable, add per-site+date
  response caching, and stop shipping CORS `*` publicly (`api/server.py` is
  HTTP/1.0 `ThreadingHTTPServer` on 127.0.0.1:8642, no keep-alive, no OPTIONS preflight).
- **PWA/offline = cheap add-on**: the chart needs no server once it has a payload, so
  manifest + service worker + cached payload gives an offline "last night".
- **Desktop/mobile = packaging, not a rewrite**: WebView shell (Tauri/Electron/Capacitor)
  around the exported UI; data from (i) a bundled Python sidecar — needs `api/server.py`
  to bind port 0 and expose a shutdown handle — or (ii) precomputed per-observer JSON
  packs for phones.
- **NINA plugin = feasible as a BRIDGE, not a port.** Plugin = one DLL exporting
  `[Export(typeof(IPluginManifest))]` under `%LOCALAPPDATA%\NINA\Plugins\3.3.0\`; NINA
  imports `IDockableVM` etc. by MEF. NINA already ships WebView2 and already anchors the
  night at 12:00 (`NighttimeCalculator.GetReferenceDate`), and samples moon altitude in
  10-minute steps — so the plugin hosts *this* chart in a dockable panel and feeds it
  NINA's own numbers. **Do not re-derive astropy in C#**: any library swap moves contact
  times by minutes and breaks every fixture/golden baseline. NINA's own astronomy is
  P/Invoke over native NOVAS/SOFA DLLs in an unchecked-out submodule anyway.
- **Ask the user before NINA work** (decisions are listed in PORTABILITY §5.5): whose
  numbers the NINA panel shows (recommend NINA's), whether the observatory PC has the
  Evergreen WebView2 runtime, how tightly to track NINA minors, separate repo or not.
